# Spike: secp256k1 wallet key and Android Keystore

Status: complete. Feeds ADR-0001 (wallet key custody) and ROADMAP Decision 1.

## Question

ROADMAP Decision 1 says the app creates a key pair and keeps it in Android Keystore. The wallet signs XRPL EVM Sidechain transactions, so the key must be on the secp256k1 curve. Can Android Keystore hold that key directly? If not, does an envelope design work, where an AES-256-GCM key that never leaves the Keystore encrypts the secp256k1 private key at rest?

## Method

An instrumented test, `KeystoreEnvelopeSpikeTest` (package `com.latifi.wallet.spike`), runs on an Android 14 (API 34, x86_64, google_apis) emulator on a GitHub-hosted Linux runner. The workflow is `.github/workflows/android-spike.yml`. It is not a required check and must not be added to branch protection, because an emulator can be flaky. It runs on pull requests that touch the test file or the workflow file, and on manual dispatch once the file exists on `main`.

The test uses throwaway keys on a throwaway emulator. It never passes key material to a logging call. The only log lines carry exception class names, exception messages and Keystore security-level flags.

Dependencies for the spike are declared for `androidTest` only: `org.web3j:crypto` and `org.web3j:utils` at `4.12.3-android`, plus `org.bouncycastle:bcprov-jdk18on` at `1.78.1`. The release classpath of the app is untouched.

## Results

Evidence run: https://github.com/Arquitectura-de-Softwares-Emergentes/latifi-android/actions/runs/40944177984

The instrumentation report shows `KeystoreEnvelopeSpikeTest` with tests=3, failures=0, errors=0, skipped=0, and the job concluded `success`.

### Q1: direct secp256k1 in the Keystore

Method `q1DirectSecp256k1IsRejectedByKeystore`. Initializing an `AndroidKeyStore` `KeyPairGenerator` for algorithm EC with the curve `secp256k1` fails. Recorded output:

```
Q1 exception class: java.security.InvalidAlgorithmParameterException
Q1 exception message: Unsupported EC curve name: secp256k1. Supported: [ed25519, p-224, p-256, p-384, p-521, prime256v1, secp224r1, secp256r1, secp384r1, secp521r1, x25519]
```

Result: confirmed. Android Keystore cannot generate or hold a secp256k1 key.

### Q2: envelope round trip

Method `q2EnvelopeRoundTripSignsWithRecoveredKey`. The test creates a 256-bit AES-GCM key in `AndroidKeyStore`, generates a secp256k1 pair with web3j `Keys.createEcKeyPair`, encrypts the 32-byte private key with a random 12-byte IV into an app-private file and zeroes the in-memory copy. It then decrypts the file, signs a fixed message with `Sign.signPrefixedMessage` (EIP-191 prefix) and recovers the signer. The recovered address equals the address derived from the original public key, and the recovered public key equals the original.

Result: confirmed. The wrapping key reports no exportable bytes (`encoded` is null) and `KeyInfo.keySize` is 256.

### Q3: no plaintext at rest

Method `q3NoPlaintextKeyInAppStorage`. After wrapping a fresh key, the test scans every file under `filesDir`, `cacheDir` and `databases` for the raw private key bytes and for its hex string. Neither appears, the scan covers the wrapped file, and the wrapped bytes still decrypt to the original key.

Result: confirmed.

## Caveats

- The emulator Keystore is software backed. The log of the same run shows `Q2 AES key insideSecureHardware=false` and `Q2 AES key securityLevel=0`. This spike proves the envelope logic and the API behavior. It does not prove hardware (TEE or StrongBox) protection on a real device. A physical device check belongs to the Phase 5 wallet work.
- The `-android` web3j artifacts publish no transitive dependency metadata, so `org.web3j:utils` and BouncyCastle are declared by hand. Android also ships a stripped provider named `BC`. The test replaces it with the bundled BouncyCastle (`Security.removeProvider` then `Security.insertProviderAt`) before calling web3j. The production wallet must do the same.
- `KeyInfo.isInsideSecureHardware` is deprecated in the SDK. The Phase 5 code should read `KeyInfo.securityLevel` instead.

## Verdict

The envelope design is confirmed on an API 34 emulator. Android Keystore rejects secp256k1 outright (Q1), and an AES-256-GCM key held in the Keystore can wrap a web3j secp256k1 private key, unwrap it and still sign correctly (Q2), with no plaintext key in app storage (Q3). Hardware-backed protection is not demonstrated by this run.

## Consequences for ADR-0001

- Android Keystore holds only the AES-256-GCM wrapping key. The secp256k1 private key is generated by web3j and stored wrapped.
- The BIP-39 recovery phrase stays mandatory. The wrapped key is bound to the Keystore of one device and cannot be exported or restored on a new device, so the phrase is the only recovery path.
- The wallet code must register the bundled BouncyCastle provider before any web3j call.
- A real-device check of the security level of the wrapping key is a Phase 5 follow-up.
